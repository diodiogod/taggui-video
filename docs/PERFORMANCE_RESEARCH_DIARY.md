# TagGUI performance research diary

## Important findings

- Browsing and page jumps are smoother in live-folder checks.
- Large workflow files stay out of ordinary page loading.
- Image switching avoids flashes; zoom does less repeated work.
- Text search matching is consistent; Quick Sort counting keeps the interface available.
- Startup does less repeated setup, and window cleanup is safer.
- First-video setup now avoids unused audio work; a separate library-loading delay remains.

This diary records research findings and implementation measurements. See [the implementation log](PERFORMANCE_IMPLEMENTATION_LOG.md) for delivery status and operational history. The earlier phases describe the original audit baseline.

## First-video audio attribution and deferred setup — 2026-10-03

**Startup lifecycle correction:** The closing guard added in the prior phase lacked constructor initialization. `MainWindow.__init__` now initializes `_main_window_closing = False`. The startup test exercises real `restore()` with an isolated saved directory and dock position and waits for deferred delivery; asserting teardown alone had missed the functional regression. Both restore and early-close cases pass. No performance claim or real-settings mutation accompanies this correction.

- **Area/files/functions:** `VideoPlayerWidget.__init__`, `_load_qt_media_source_for_current_video`, `_ensure_qt_audio_output`, MPV/VLC setup, `set_muted`/`set_volume`; `tests/probe_video_first_use.py`, `tests/test_lazy_video_audio.py`.
- **Questions:** Which native constructor accounts for first-use cost? Does an external backend need Qt audio? Can fallback preserve current mute, volume and playback intent?
- **Sources:** [Qt 6.9 audio source](https://github.com/qt/qtmultimedia/blob/v6.9.0/src/multimedia/audio/qaudiooutput.cpp) shows default-device lookup and platform output creation in the constructor. [Qt 6.9 player source](https://github.com/qt/qtmultimedia/blob/v6.9.0/src/multimedia/playback/qmediaplayer.cpp) supports attaching audio separately. [Audio properties](https://doc.qt.io/qt-6/qaudiooutput.html) document normalized volume and mute state.
- **Observed measurements:** Constructor-only line tracing attributed 292.536 ms to QAudioOutput and 59.720 ms to QMediaPlayer in one fresh-process run. First MPV load in that run took 2195.514 ms, with 2164.681 ms directly inside `_ctypes.LoadLibrary`; this confirms DLL loading attribution for this sample, not its internal Windows cause. Earlier warmer library samples were approximately 32–34 ms.
- **Implementation/benefit:** Keep audio intent in lightweight fields; create a parent-owned Qt output only before a Qt source is loaded, including external-backend fallback. External backend setup receives stored mute/volume. QMediaPlayer remains eager to preserve its many consumers. No playback/reveal scheduling changed.
- **Result:** New fresh-process constructor samples 3.440 and 3.618 ms. Explicitly invoking deferred Qt audio setup in the latter process still cost 296.213 ms: the cost is avoided for external playback, not magically eliminated for Qt. Generated preview paths still pass; these are individual isolated samples, not full click-to-visible measurements. Six new tests cover external preview without Qt audio, controls, native fallback attachment/ownership and retained intent; existing global-toggle/paused/playing transition tests also pass.
- **Confidence/effort/risk/GUI:** High confidence in avoiding unnecessary construction; small effort, low-to-medium audio compatibility risk. Check real mute/volume, first playback, switching videos and Qt fallback. Audible output and native first-frame timing remain unverified by offscreen tests.
- **Decision:** Implemented audio deferral. Background DLL loading remains uncertain: `_BACKEND_LOAD_ATTEMPTED` is published before import completes, so concurrent resolution could falsely fall back. A blocking lock alone would move the wait back onto the GUI. Need a pending/ready/failed contract and owned continuation before enabling asynchronous import; reject blanket startup preloading and unsafe native-widget worker creation.
- **Follow-up verification:** Full collection initially crashed during Quick Sort fixture event delivery. `tests/test_quick_sort_panel.py::_dispose` only hid native windows; it now drains the count worker, explicitly destroys the root and asserts child invalidation. Full suite then passed **578 tests, four skipped**, normal GC. This corrects a fixture lifetime violation without attributing the crash to the audio change. Runtime resolution also has synchronous consumers in `SettingsDialog` and sync-start priming; an async design must cover those consumers, not just initial image selection.

## Startup construction and native style ownership — 2026-10-03, investigation

- **Area/files/functions:** startup/Qt lifecycle; `MainWindow.__init__`, `_restore_after_init`, `_sync_left_folder_companion_handle`; `ImageListView.__init__`, `ImageListScrollBarTrackStyle`; `IdeogramCaptionEditor.__init__`/`_apply_ui_zoom`; `PipelineEditor.__init__`/`_apply_ui_zoom`; opt-in `tests/probe_startup_followup.py`.
- **Questions/searches:** Which panel construction work blocks the first event-loop turn? Who owns a QProxyStyle base style? Search: Qt QProxyStyle ownership, per-widget application style and shutdown crashes. Trace actual constructors and cProfile callers rather than infer the cost from file size.
- **Sources:** [Qt QProxyStyle documentation](https://doc.qt.io/qt-6/qproxystyle.html) explicitly transfers base-style ownership to the proxy and prescribes a separate style created from the application style name for one-widget overrides. [QWidget style ownership](https://doc.qt.io/qt-6/qwidget.html#setStyle) states that the widget does not take ownership of the assigned style; parent the local proxy to its owner. [Qt styling guidance](https://doc.qt.io/qt-6/qtwidgets-styling-approaches.html) explains stylesheet parsing and descendant repolishing. Installed Qt behavior and the current source supply the project-specific evidence.
- **Observed result:** A fresh isolated, profiled empty window took about 341 ms to construct and about 101 ms from construction completion to the first GUI timer. Import took about 434 ms in that subprocess; the runner had already created Qt/settings. These are diagnostic timings, not end-to-end real-folder startup measurements. Stylesheet calls consumed about 106 ms self-time; the Auto-Captioner inherited styles accounted for about 44 ms, while the Ideogram panel and Pipeline applied styles twice before first display.
- **Failed probe and diagnosis:** Native DeferredDelete crashed repeatedly with the Windows process-exit failsafe disabled. Draining workers, detaching model/scene consumers and removing the app-wide event filter did not resolve it. Ordered native-child destruction localized it to ImageList. `ImageListScrollBarTrackStyle(QApplication.style())` transferred the shared application style to a view-owned proxy. Using the documented string/name constructor creates a separately owned base. This removed the native crash, exposing a queued folder-handle callback that read an already destroyed dock; closing-state guards now reject that callback and pending startup restoration. Explicit native root deletion and subsequent event delivery now pass. The Windows exit failsafe is retained; this does not prove all media/backend shutdown cases safe.
- **Technique/mapping/benefit:** Give each browser its own scrollbar style; never lend the global style to an owning proxy. Prevent already queued initialization/layout callbacks from accessing a closed window. Expected benefit is lifetime correctness and safe multi-browser disposal, not a claimed browsing speed gain. Duplicate initial panel styling is a separate, small startup hypothesis to measure before claiming a benefit.
- **Confidence/effort/risk/GUI:** High confidence in the ownership contract and reproduced empty-window teardown correction; small effort, low-to-medium GUI-style compatibility risk. GUI check required for scrollbar appearance/dragging, secondary-browser hide/show and window closing. Broad lazy panel construction remains deferred because of direct signal access and saved-layout/first-open tradeoffs.
- **Experiment/result/decision:** Explicitly destroy multiple real browser widgets while retaining the application style, models and a sibling widget; compare scrollbar geometry/hit-testing and paint behavior. Add a full-window close-before/after-first-event regression with the failsafe disabled. Measure the duplicate-style removal independently using the same final CSS/zoom state. Ownership/callback fixes are implemented; regression and styling measurements are in progress.

### Completed follow-up: lifetime-bound callbacks and duplicate styling

- **Additional source/evidence:** [Qt context-bound singleShot](https://doc.qt.io/qt-6/qtimer.html#singleShot-5) specifies that delivery is canceled when the context QObject is destroyed; [PySide's exposed overload](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QTimer.html#PySide6.QtCore.QTimer.singleShot) documents `(msec, context, functor)`. [QObject destruction](https://doc.qt.io/qt-6/qobject.html#dtor.QObject) documents child deletion and automatic signal disconnection. The installed pinned PySide 6.9 binding passed an alive-versus-destroyed-context test.
- **Observed problem/mapping:** Broader close-before-first-event and repeated-window tests exposed unowned sort-label, toolbar-clamp, activation-restore and pipeline-connector callbacks. Relevant schedules in `image_list_dock.py`, `auto_markings.py`, `toolbar_manager.py`, `main_window.py` and `PipelineStepList` now carry their native UI context. Delays and normal callback logic are preserved. `MenuManager` is now a window-owned QObject and a native slot receives application focus changes directly; the previous global lambda could retain a destroyed window and later access deleted Undo/Redo actions. Closing-state checks also reject restoration/menu work while a closed window is still natively alive. This is a targeted lifecycle correction, not proof that every application callback has a complete lifetime contract.
- **Verified styling change:** `IdeogramCaptionEditor.__init__` keeps the same base CSS string and applies it with zoom rules once, rather than polishing descendants twice. `PipelineEditor.__init__` similarly uses its existing final `_apply_ui_zoom` styling pass. Both remain constructed eagerly, preserving current field/signal availability and saved-layout behavior.
- **Measurement:** `tests/probe_panel_startup.py` extracts only the two constructors from checkpoint `1cbc935`, supplies their unchanged real widget dependencies, and compares them with current constructors under Fusion. One warm-up pair, five alternating-order samples per version at 60/100/160% UI zoom. At 100%: Ideogram **28.860 → 16.758 ms**, Pipeline **12.799 → 8.119 ms** median. Final CSS and rendered pixels match exactly at all three sizes. A combined-probe repeat yielded **29.726 → 17.372 ms** and **13.073 → 8.189 ms**. Roughly 17 ms less construction work across these panels; no end-to-end startup or real-folder speedup claim follows. Running multiple probe modules together preloads imports during pytest collection, so their import timings are not comparable with an individually invoked fresh-process startup probe.
- **Confidence/effort/risk/GUI:** Styling: small measured startup impact, high confidence in these comparisons, small effort, low risk. Lifecycle: correctness/stability impact, high reproduced confidence, medium combined effort, low-to-medium regression risk. GUI testing required for scrollbar drag/appearance, secondary-browser visibility, Ideogram/Pipeline opening and Ctrl+wheel resizing, Undo/Redo after focus changes, and normal exit.
- **Regression result:** Two real browser styles retain independent base objects, application parent/proxy identity and unchanged thumb geometry/hit-testing; native browser destruction leaves the sibling browser/application style usable. Actual windows are explicitly destroyed before and after startup delivery, with delayed connector callbacks queued, workers drained and Windows failsafe disabled. Complete isolated suite: **572 passed, four skipped**, 38.35 s, normal GC and no excluded modules. All three opt-in probes also passed together. Original native-failure steps and failed fixture assumptions remain recorded above; no failure is hidden by GC suppression or forced process exit.
- **Decision:** Implemented. Keep broad lazy-panel and video startup redesigns measurement-led.
- **Fresh-process probe check:** Individually invoked after the fixes under production Fusion style: import 432.310 ms, construction 337.371 ms, first timer 93.526 ms after construction; 113 stylesheet calls / 91.792 ms self-time. Explicit root deletion succeeded. This single current diagnostic is not a matched whole-startup speed comparison, since the earlier diagnostic used the platform default style and a different native ownership path.

- **Area/files/functions:** `ImageViewer.load_image` → `_ensure_video_components` → `VideoPlayerWidget.__init__`/`load_video` → `_refresh_backend_selection` → `resolve_runtime_playback_backend`/`load_playback_backend`; metadata/preview admission through `_apply_metadata_hints`, `_set_initial_preview_pixmap`, `_ensure_cap_ready`; `utils/video/mpv_runtime.py`; opt-in `tests/probe_video_first_use.py`.

Read installed python-mpv 1.0.8 library discovery/loading and Qt media startup contracts; search/open its exact tagged implementation rather than infer costs from a worker count.
- **Sources:** [python-mpv v1.0.8 source, Windows loading](https://github.com/jaseg/python-mpv/blob/v1.0.8/mpv.py#L39-L65) searches DLL names and calls ctypes CDLL during module import, before any MPV player is created. [Windows LoadLibraryEx](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexa) documents DLL/dependency loading and initialization. [Qt QMediaPlayer](https://doc.qt.io/qt-6/qmediaplayer.html#setSource) distinguishes source assignment from asynchronous media-status readiness. These establish mechanisms; they do not attribute the entire first-use delay to a particular driver or filesystem operation.
- **Observed implementation:** Default backend is MPV (`video_playback_backend='mpv_experimental'`); auto-play defaults off in `VideoControlsWidget`. The video components already initialize lazily. `load_video` still resolves the optional backend synchronously, even with indexed metadata and preview pixels, and falls back to synchronous OpenCV capture when either is missing. MPV instance/native surface creation is already deferred until play; cached preview support is already implemented. Do not recommend it as a missing feature.
- **Isolated experiment/results:** Generate a 1920×1080 MJPEG AVI containing 12 frames under a temporary root. OpenCV is warmed by fixture creation. Measure a standalone paused player and first GUI timer; no main-window signal fan-out, video controls, native playback surface or click-to-visible measurement is included. Individual fresh subprocesses took **281.580/284.542 ms** to construct the player. Initial metadata+preview load took **2,178.310 ms** once; a subsequent fresh process took **48.415 ms**, with ctypes LoadLibrary accounting for **33.714 ms** self-time. Warm metadata+preview then took **5.765 ms** with no capture opened; missing preview took **30.191 ms**, missing both took **22.754 ms**, opening capture in both cases. These are individual samples, not medians. Cold versus warm OS/library cache is a plausible explanation for the large variation, not a verified attribution. cProfile groups most constructor cost under `VideoPlayerWidget.__init__`; finer tracing is needed before blaming a specific Qt object/device. A combined-probe run confirmed about 284 ms construction and 5.778 ms warm preview loading.
- **Expected benefit/confidence/effort/risk:** There is measured first-use work worth investigating; no new video speedup has been implemented or proven. Confidence high in the observed call path and prepared-preview capture avoidance, medium in cold-library attribution. A complete asynchronous preparation or Qt-fallback-lazy strategy would be medium-to-large effort and medium-to-high playback/Windows regression risk; GUI testing is essential. Native QObject/media surfaces must stay on their owning Qt thread.
- **Concrete next experiment:** Use a fresh real Windows session and ETW/sample stacks around first and repeated MPV selection, separating module/native-library load, Qt player/audio construction, controls creation, preview paint, backend file-loaded and surface reveal. Test indexed metadata with ready/missing thumbnails, initial paused/playing intent, an immediate second selection and a global toggle while preparation is pending. Compare UI timer/input availability and first visible correct frame, without flushing production caches. Only then prototype immutable request-owned preparation or a lazy Qt fallback with cancellation/error/intent parity.
- **Rejected/deferred:** Do not blindly preload every optional backend at startup (adds unused work/threads and import-race concerns), create native Qt media objects on a generic worker, remove reveal gates, or delay preview until playback readiness. Do not replace full-size preview scaling with a thumbnail transform without checking editing coordinates, scene geometry and zoom behavior.
- **Decision:** Uncertain / measurement-first. Preserve current video behavior for this batch; this is a focused remaining candidate rather than an exhausted area.

## Text-search consistency across predicate paths — 2026-10-03

- **Area/files/functions:** `ProxyImageListModel.does_image_match_filter`, `is_image_in_filtered_images`, `_relative_search_path`; `ImageListModel._build_filter_sql`; shared `utils/search_text.py`; actual `FilterLineEdit.parse_filter_text`; `tests/test_search_text_parity.py`.
- **Question/searches:** Can the live-image predicate preserve default paginated results without querying SQLite or retaining captions? Searches/readings: SQLite LIKE ASCII case rules and wildcard syntax; Python fnmatch translation. Current `pagination_threshold` defaults to 0: both small and large folders normally paginate. The proxy predicate is also used by edit/undo membership checks, so a legacy implementation is not necessarily unreachable.
- **Sources:** [SQLite expression documentation, LIKE](https://www.sqlite.org/lang_expr.html#like) specifies ASCII-only case folding and `%`/`_` patterns; Unicode beyond ASCII remains case sensitive. [Python fnmatch documentation](https://docs.python.org/3.12/library/fnmatch.html) specifies glob translation and case-sensitive matching. Installed Python 3.12 translation uses atomic interior star groups, avoiding a naive chain of backtracking regex wildcards. TagGUI's unchanged SQL is the compatibility baseline.
- **Technique/mapping:** Share pattern construction between SQL and the live predicate. A pure, IO-free LIKE matcher converts SQL wildcards to glob syntax, escapes glob characters which LIKE treats literally and folds ASCII only. Cache at most 256 compiled patterns; patterns longer than 4,096 characters bypass that cache, and no captions are cached. Preserve exact case-sensitive tag equality and existing wildcard-tag LIKE behavior. Plain/caption searches check individual tags and structured text separately, and plain path matching uses the loaded-root-relative path. Palette searches inspect palette chips rather than arbitrary structured prose. Empty structured-text membership respects whether a corresponding sidecar/index row can exist. Name/path/marking glob semantics retain their separate implementation.
- **Expected benefit/confidence/effort/risk:** Correctness and consistent edit-time membership, no claimed speed gain. High confidence in tested text cases and preserved SQL outputs; medium effort, medium compatibility risk for users explicitly choosing nonpaginated mode (its previous results can change); low expected impact on default paginated browsing. GUI testing useful for searches and editing/undo under an active filter.
- **Experiment/result:** Compare 1,500 deterministic random patterns plus curated ASCII/Unicode/punctuation/newline/NUL cases directly against SQLite `SELECT ? LIKE ?`. Use the real filter-box parser and real isolated indexed fixture for tag/plain/caption/Ideogram/palette/AND/OR/NOT queries, numeric smoke cases, and per-image membership with pagination enabled. Explicit expected result sets freeze the previous paginated cases, including literal brackets and phrases spanning separate tags. The first harness incorrectly passed the parser's outer list; it was corrected to call `parse_filter_text` exactly as the application does. Non-ASCII test terms were quoted to match the existing grammar. No application parser changes were made.
- **Regression result:** Complete isolated suite **568 passed, four skipped**, 38.81 s; no excluded modules, normal GC. Only generated fixture files/databases and explicit temporary settings/cache/home roots were used.
- **Decision:** Implemented text-predicate parity against current paginated behavior. This does not redesign search syntax or claim that database freshness, tokenizer failure handling, target-size predicates or every malformed internal filter now have an identical contract. Those require their own evidence. No default search result changes or new GUI-time DB queries were introduced by this batch.

[SQLite isolation](https://www.sqlite.org/isolation.html) specifies committed-transaction visibility between connections. [Shiboken type-system documentation](https://doc.qt.io/qtforpython-6/shiboken6/typesystem_manipulating_objects.html) provides binding-generation background, not proof that the installed QImage overload releases Python execution. Worker submit/result **0.046/43.304 ms**, first timer **2.740 ms**, 14–16 callbacks before delivery. ## Zoom follow-up: eliminate repeated conversion — 2026-10-03

- **Area/files/functions:** `ImageViewer._get_static_mipmap_pixmap`, existing full-size `_static_mipmap_pixmaps[1]`; `_static_source_qimage` consumers `_sample_image_color_at_scene` and dominant-color extraction. Tests: `test_mipmap_display_source.py`, `probe_async_mipmap.py`.
- **Question/search:** Is the slow alpha-capable image scaling dominated by conversion that the existing display pixmap already performed? Searches: Qt QImage smoothScaled implementation, premultiplied alpha performance. Inspected pinned upstream code using GitHub's raw-content API.
- **Primary evidence:** [Qt 6.9.0 qimage.cpp](https://github.com/qt/qtbase/blob/v6.9.0/src/gui/image/qimage.cpp), `QImage::smoothScaled`, explicitly converts nonpremultiplied alpha formats before `qSmoothScaleImage`; RGB32 and premultiplied formats bypass this conversion. [Qt QImage documentation](https://doc.qt.io/qt-6.8/qimage.html) identifies RGB32/premultiplied ARGB32 as optimized rendering formats. Source code provides the specific scaling mechanism, rather than extrapolating the rendering guidance alone.
- **Technique and mapping:** For 8-bit ARGB32/RGBA8888 sources only, reuse the existing full-resolution display pixmap's `toImage()` when dimensions match and its format is RGB32/premultiplied ARGB32/RGBA8888. Run the same Qt smooth scaler, rounding, divisor and GUI pixmap installation. Keep the original source for precise color sampling; do not change high-bit-depth formats, decoding, image files, compare preparation or cache budgets. Existing implicit sharing avoids a separate persistent full-image copy. Missing/incompatible display pixels retain the old path.
- **Experiment/result:** Same isolated generated 6000×4000 ARGB32 quarter-scale probe, seven samples, real production getter versus exact checkpoint `0d0a53f`. Checkpoint median handler/installation/first timer **52.094/52.099/52.141 ms**; retained worker-only prototype **0.075/57.383/53.536 ms**; new display-source path **3.239/3.242/3.258 ms**. This measures the previously uncached zoom resize with an already-created full-size display pixmap, not complete decoding or real monitor paint latency. The existing display-pixmap conversion cost is not hidden as new preparation; both paths already require that pixmap.
- **Parity:** Forty randomized combinations of ARGB32/RGBA8888/RGB32/RGBA64, opaque/varied alpha, odd dimensions and divisors 2–32 produce identical displayed ARGB32 pixels to the original scaling; color-space equality, unchanged original image and cached reuse are checked. An additional missing-display-source test covers fallback. No alternate interpolation or destructive alpha conversion was introduced.
- **Benefit/confidence/effort/risk/GUI:** High expected benefit for uncached zoom/fit resizing of large affected PNG/WebP images; little expected gain for already-fast RGB32 JPEG or cached levels. High confidence for tested pixels/mechanism, small implementation, low regression risk with guarded fallback. GUI testing still required for fit/actual-size, rapid zoom/pan, transparency edges, crops/markings and color sampling.
- **Decision:** Implemented the conversion-reuse optimization. Continue rejecting worker placement alone; it is unnecessary for the measured cost reduction and adds lifecycle complexity. No claim that every image operation is now nonblocking.
- **Combined regression result:** Full isolated suite **521 passed, four skipped**, 32.11 s; normal GC, no module exclusions. An existing target-page test now waits for worker cleanup after queued page delivery rather than assuming those happen simultaneously. Production page loading was not changed for that test race.

## Evidence conventions

- **Observed:** visible in the current source or an explicitly attributed historical trace.
- **Hypothesis:** source-backed mechanism that may apply; no speedup claimed without measurement.
- **Verified:** demonstrated by a described isolated measurement during this audit.
- Historical benchmark results retain their original conditions; they are not new measurements or release guarantees.
- External code on moving branches is illustrative until its revision is recorded. Qt APIs must be checked against the project's PySide6 6.9.0 pin, rather than assumed available from latest documentation.

Existing cache keys should be versioned or migrated deliberately if freshness fields/algorithm change.

Exercise failure/permission/full-disk publication and acknowledge success before setting thumbnail_cached. Concurrent cache reads and atomic commit need separate generated-data tests on Windows.

- **Expected benefit/confidence/effort/risk:** high confidence in cancellation contract and reproduced false-zero fallback; medium live benefit. Potentially high obsolete-work responsiveness on expensive filters/order builds, no app speedup measured. Medium measurement effort/high implementation effort and high transaction/connection/error/selection risk; GUI required. Exercise interrupted rank-table build, fallback suppression, count/page/aggregate consistency, folder close/replacement, two browsers and write operations. Real-folder profiling should record cancel-request to worker-release and accepted-result timestamps separately.

Compare bounded dispatch at equal active worker counts, including validation progress, disk-write drain, shutdown and failures. Native bytes should be estimated from actual image sizeInBytes and corroborated by process memory, not Python tracemalloc alone.
