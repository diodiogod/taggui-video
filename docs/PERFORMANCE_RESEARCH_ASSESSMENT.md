# TagGUI performance and architecture research assessment

Research date: 2026-10-01/02. Source baseline: `45f749d` (1.6.17), PySide6/Qt 6.9.0, project venv SQLite 3.45.3. Application code was not changed during the research phase. Detailed sources, questions, probe conditions, rejected alternatives and confidence reasoning are in [the progressive research diary](PERFORMANCE_RESEARCH_DIARY.md).

**Implementation checkpoint:** The user subsequently authorized implementation, reported smooth browsing, and requested an intermediate commit. H1/H2, main-image H3, asynchronous-view/count H4, H5/H6, H7/H8 and the bounded-binding/compact-order portions of H10/M13 are now implemented. The tables and paths below describe the research baseline, rather than a claim these fixed paths remain unchanged. Current behavior, measurements, remaining candidates and caveats are in [the implementation log](PERFORMANCE_IMPLEMENTATION_LOG.md). Normal browsing feedback is positive; full feature parity and live latency improvements have not been established.

## Assessment

TagGUI has a credible incremental large-folder architecture: indexed page retrieval, resident-window masonry, worker QImage thumbnails, target-page-first jumps, balanced adjacent hydration, stale-layout identities, deferred proxy invalidation and bounded distant-pixmap eviction. Current paginated bootstrap already requests page zero asynchronously and warms its neighbors after acceptance. Recent September fixes matter: geometry-only masonry sizing no longer requests thumbnails, old layout results are rejected, and arriving upper pages preserve a visible tile anchor rather than an obsolete scrollbar value. These are already implemented, not new backlog items.

The remaining responsiveness problem crosses subsystem boundaries. A worker page loader does not make filtering, sorting, metadata refresh, aggregate counts or selection responsive when their input callbacks still perform synchronous count/rank/materialization, sidecar work, decoder reads or downstream model callbacks. `QTimer.singleShot(0, ...)` defers a call but does not move it off the GUI thread. First-use video and hidden folder-tree work also occur after some apparently successful startup milestones.

Three method-level correctness failures were reproduced against extracted current DB methods on synthetic data: descending/tied/NULL rank lookup disagrees with page order; one DB instance can trust an order-cache signature after another instance replaces its shared contents; and an order-affecting rating edit leaves an already-built rating cache stale. These can undermine landing/restoration and cause empty or obsolete pages. They are proven method contracts, not a reproduction of a particular live GUI incident.

The historical 26,848-item cold target-page materialization took about 8.30 seconds versus about 578 ms warm in the September notes. This audit did not repeat those measurements. The current path includes per-record existence checks and preferred-sidecar stat/read/cache work, plus metadata reconciliation. Synthetic indexed SQL at this size took only a few milliseconds, but that does not isolate the real database or prove filesystem work accounts for the historical gap. Measure that decomposition before schema or hydration redesign.

Scaling toward one million items is conditional. Resident pages do not bound native pixmaps, viewer/decoder allocations, executor backlog, deferred cache-save images, SQLite rank tables or retained runtimes. Deep/random page retrieval already uses a materialized rank cache; recommending OFFSET replacement as though every deep request currently scans skipped rows would misdescribe the implementation. The important questions are cache correctness, build amortization, filter cost and end-to-end memory ownership.

No real-folder GUI improvement was measured or claimed. External implementations are mechanism evidence, not proof of suitability: Gwenview's all-row thumbnail scan is unsuitable for TagGUI's million-item goal; archived digiKam source illustrates historical scheduling patterns rather than current product behavior; browser virtualizer timeouts and iOS workarounds are not Windows Qt policies.

### Million-item implications from isolated measurements

The synthetic SQL probe used simplified generated rows and warm SQLite queries, without media, sidecars, migrations, Qt callbacks or actual TagGUI cache-table schema. Its values identify mechanisms; they are not projected folder-load times.

| Generated workload | 26,848 images | 1,000,000 images | Implication for current TagGUI |
| --- | --- | --- | --- |
| Indexed mtime page at first/deep offset | about 1.9–2.3 ms | about 1.7 ms first, 15.1 ms at 500K, 27.6 ms near end | OFFSET grows with depth, but is not automatically the dominant page cost. Current deep pages already select the rank-cache path at offsets >=50K. |
| Indexed sequential keyset with known pivot | about 1.7 ms | about 1.7 ms | Good sequential primitive; does not answer arbitrary index jumps without a pivot/rank mapping. |
| Unindexed area ordering, deep raw OFFSET | about 47.8 ms | about 17.5 s | Derived sorts can be expensive. This deliberately uncached raw query is **not** the current deep-page TagGUI execution path. |
| Synthetic area rank-table build / lookup | about 59.6 / 1.7 ms | about 1.91 s / 1.8 ms | Rank construction must be amortized and correctly owned/versioned; rapid filter/order churn can keep paying the build cost. Actual durable composite-key cache costs may differ. |
| Exact area-expression index, deep offset | about 2.3 ms | about 26.8 ms | Indexing can remove the sort but does not remove skipped-row work. Compare storage, writes, filter plans and order-cache alternatives. |

At one million items, the objective should be bounded *active* state, not a claim that every persistent order structure is constant-sized. Inventory Python resident records, queued/running/ready QImages, GUI pixmaps, viewer/mipmap images, native video surfaces, writer backlog, SQLite page caches and retained runtimes separately. Estimate image bytes from actual dimensions/stride; item-count limits alone do not control portrait/panoramic/large-media allocations. Track sharing so multiple references to one QImage are not falsely counted as independent pixel buffers. Use process/native memory measurements alongside these estimates; this audit did not measure the real application's peak memory.

## Critical paths examined

| Trigger | Current path and unresolved cost |
| --- | --- |
| Filter text / media filter | `SignalManager` connections → MainWindow filter debounce/apply → `ImageListModel.apply_filter` → synchronous DB count and page hydration → reset/proxy remap → tag counts, selection restore, delegates, paint. Count UDFs can execute Python and filesystem predicates. |
| Sort or searchable metadata edit | `ImageList._on_sort_changed` resolves rank and synchronously prepares target/initial pages; `ImageListModel._refresh_paginated_filter_after_metadata_change` synchronously recounts and reloads resident pages. Reset delivery can invoke more work. |
| Selection | `SignalManager.connect_image_list_signals` nested `safe_load_image` first updates caption metadata; viewer `_load_image_impl` reads the full image synchronously. `safe_load_tags` flushes previous edits and reads incoming metadata/tags. `dataChanged` can reload the viewer and recount tags. |
| Scroll / jump | Accepted layout visibility/hit testing → priority queues → executor dispatch → QImage completion → GUI decoration conversion/paint → dimensions/relayout → proxy invalidation and selection callbacks. Most ownership protections exist; native conversion, locks, queue pressure and repeated scans need actual latency attribution. |
| Folder switch / startup | `ImageListModel.load_directory` opens/migrates/counts index; `_load_directory_paginated` already queues initial page hydration. Constructor/count work and reset callbacks still need attribution. `MainWindow.load_directory` logs `ui-setup-returned` before `FolderTreePanel.set_root` recursively scans and constructs items, even when hidden. |
| Missing indexed file | Worker page materialization reports missing paths → GUI `_on_page_loaded_signal` → `_on_stale_index_paths_detected` → synchronous prune/count → reset and `_load_page_sync` for every resident page. Correctness repair exists, but worker discovery does not bound its GUI repair cost. |
| First video / replacement | `VideoPlayer.load_video` may synchronously probe/decode a preview; lazy MPV setup constructs native/GL objects. Core command return, file-loaded, successful render and visible reveal are different milestones. |

H1 and H2 are correctness prerequisites, not claimed performance wins. For H3/H4, moving one call off-thread is insufficient: follow model resets, selection signals and GUI result installation through to paint. Request cancellation must be distinguished from interruption of a running SQL query or native decoder. Qt requires GUI-owned model notifications; see [model thread-affinity requirements](https://doc.qt.io/qt-6.5/qabstractitemmodel.html).

Evidence for M2/M3: the extracted aggregate on synthetic 26,848 rows/402,720 tags changed from approximately 204 to 82 ms for broad aggregation with a reverse covering index, but selective image-first plans barely changed. The index added about 8.5 MB. A cheap Python predicate was evaluated 402,720 times in the existing joined plan versus 26,848 with a materialized matching-ID CTE; timings were about 224 versus 46 ms. Actual TagGUI predicates and real-folder plans were not measured. See [SQLite covering-index explanation](https://www.sqlite.org/queryplanner.html) and [materialization contract](https://sqlite.org/lang_with.html#materialization_hints).

Evidence for M6: generated 4096×3072 JPEG scaled reads were roughly 86 versus 153–165 ms full; PNG/WebP had no corresponding native speedup. A second 16-case EXIF/crop probe preserved candidate bounds but found a naive rotated-crop height mismatch and nonzero pixel differences. [Qt's pinned JPEG implementation](https://github.com/qt/qtbase/blob/v6.9.0/src/plugins/imageformats/jpeg/qjpeghandler.cpp) supports the mechanism; it is not a GUI latency guarantee.

Evidence for M7: generated 1K/8K/20K resident-layout query medians were 0.087/0.568/1.394 ms for the current scan versus about 0.02 ms for column lookup, with builds of 0.115/1.419/5.054 ms. All generated query sets matched. This does not establish real layout/hit-test parity or make this the highest-priority task.

A practical extraction sequence for A1–A4 is to define contracts before moving implementations:

- **Ordered view request:** folder/database identity, filter/bindings, canonical sort/seed and order-affecting revision; count/rank/pages/totals describe the same accepted view. A thumbnail-cache flag is not an order revision.
- **Resident mapping snapshot:** local row, global rank and stable media identity must agree throughout GUI installation and eviction. Insert/remove/reset notifications and persistent selection behavior are explicit; retaining a QModelIndex across a reset is not ownership.
- **Selection request:** outgoing-edit flush precedes accepting incoming content; bounded decode returns data/errors without touching GUI objects. Accept only the latest compatible folder/view/media request. Background path repair proposals require owned application before mutation.
- **Thumbnail demand:** distinguish queued demand from running work, completed bytes and disk-save retention. Cancellation removes demand; it does not promise to interrupt native decoding. Negative caching requires freshness and a retry policy.
- **Installed layout snapshot:** geometry identity, index map, optional column intervals and anchor reference install atomically. Upper-content translation and user supersession have explicit owners; paint and hit testing read the same accepted snapshot.

These are proposed architectural boundaries, not new behavior or approved implementation. Apply them incrementally around existing services, with narrow invariants and the GUI parity scenarios above.

## Original three implementation priorities (now addressed)

1. **Canonical ordered-view correctness (H1 + H2).** Reproduce page/rank equivalence, NULL/tie cases, two connections and order-affecting edits in permanent isolated tests, then correct the cache/rank contract. Stable identities are prerequisites for reliable performance experiments and saved-selection/jump behavior. This is the strongest verified finding; it does not promise a speedup.
2. **Bounded latest-selection image loading (H3).** Remove the known full decode from the selection input path while preserving outgoing edit flush, incoming metadata, zoom, errors and image/video ownership. Instrument decode, native conversion/install and first paint together. This targets an obvious synchronous boundary and avoids a framework rewrite.
3. **Asynchronous owned filter/sort/metadata refresh (H4).** Prepare the full request off-thread and install only its accepted target window; coalesce aggregate results and hydrate neighbors after landing. This fixes a broad family of synchronous paths rather than one debounce timer. Start with the measured worst workflow and preserve full filtered totals and selection semantics.

H5 is a useful smaller independent startup task. Preserve recursive media counts and folder-operation contracts; QFileSystemModel still delivers icon/update work to the GUI and is not a drop-in count-preserving replacement (phase31). M1 should accompany task 3 so staged page hydration is chosen from evidence. Native JPEG scaling is a bounded subsequent candidate, subject to the explicit crop/orientation/quality gate.
